## Reached mechanism

Both nullable and required setters contain the same complete dirty transition at [columns.cr:421](/Users/crimsonknight/personal_coding_projects/.luna/atlas-work/grant/src/grant/columns.cr:421) and [columns.cr:538](/Users/crimsonknight/personal_coding_projects/.luna/atlas-work/grant/src/grant/columns.cr:538). After typed normalization/conversion, each setter compares old/current database values, lazily creates the originals hash, records the original once, compares against that original, and either removes or stores a pending pair. The stored original has the broad `DirtyValue` union. This bookkeeping depends on values, an attribute key and two hashes; its algorithm does not require a concrete model or column type.

The typed guard, normalization hook, converter, actual ivar store, raw-input discard and after-assignment hook belong at the generated perimeter. The original/pending storage is already explicitly nullable and lazy at [base.cr:497](/Users/crimsonknight/personal_coding_projects/.luna/atlas-work/grant/src/grant/base.cr:497), [base.cr:545](/Users/crimsonknight/personal_coding_projects/.luna/atlas-work/grant/src/grant/base.cr:545) and [base.cr:550](/Users/crimsonknight/personal_coding_projects/.luna/atlas-work/grant/src/grant/base.cr:550). A candidate can preserve those ivars and their lazy semantics while moving the repeated algorithm. An unchanged assignment returns the original hash references, including nil/nil. A later value returning to the stored original removes only its pending change and retains the first original baseline. A present nil original remains distinguishable from an absent key through the existing `has_key?` check.

There are two different costs to discriminate. First, putting both compared values into fixed `DirtyValue` fields widens the old/current comparison for a scalar setter that originally had narrower inferred inputs. Sharing that broad comparison can add compiler work even when generated code shrinks. Second, moving the hash transition out of each generated model/field removes repeated inference and lowering of that algorithm. A direct original/full-kernel pair confounds them. The minimum discriminating design below adds a fixed-carrier comparison-only control, so both candidates pay the same intended canonical comparison boundary before measuring transition sharing.

## Concrete minimal experiment

As a Grant maintainer, I want to record a column assignment's dirty change through one value-based computation while retaining its typed column behavior. When a column has passed its readonly guard and normalization hook and tracking is active, then capture its old/current database values and current hash references, compute the original/pending change once, install the returned references, and finish the existing typed write hooks in their current order.

The source design uses two internal immutable value structs, `Grant::Dirty::CapturedColumnAssignment` in `src/grant/dirty/captured_column_assignment.cr` and `Grant::Dirty::RecordedColumnAssignment` in the matching file. The captured value holds `attribute_name`, `previous_database_value`, `current_database_value`, `collection_of_original_attribute_values` and `collection_of_pending_attribute_changes` with fixed types. Both database-value fields use the existing `Grant::Base::DirtyValue`; both hash-reference fields retain their exact existing nullable types. The recorded value holds the two resulting nullable references. New names pass the local AED name checker.

An internal pure computation `Grant::Dirty.record_column_assignment` in `dirty.cr` takes the captured struct and returns the recorded struct. It reads the broad value fields from that fixed carrier, preserving the current equality, `has_key?`, delete and pending-pair operations. Its signature contains one concrete value type and no model receiver. Generated setters construct the capture only inside the current tracking branch and install the returned hash references; typed conversion and write hooks retain their current expressions and order. This is a design proposal. Crystal source, API-card proof and a runnable overlay have not been authored.

The comparison-only control uses the same captured type and an internal fixed-carrier `has_equal_assignment_values?` computation. It substitutes that comparison at the two original comparison sites and leaves the hash-transition block in each setter. For the second comparison, capture the retrieved original/current values through the same typed fields. The full-transition candidate uses exactly that same comparator from its shared transition, including the original/current second capture. Comparing original → comparison-only diagnoses the full effect of canonicalizing the comparisons; comparison-only → full transition diagnoses moving the repeated state algorithm, with actual carrier/copy and call differences retained. Each candidate must prove the same canonical comparator owner; a two-argument union restriction does not substitute for that proof.

Minimum source boundary: comparison-only changes the two setter blocks, `dirty.cr` and one new captured-value file; the full transition adds the returned-value file and replaces only the repeated transition in those same setter blocks. Existing Base ivars, public setters, lifecycle/transaction methods, hydration, queries, associations and default features retain their source. The shared helper is a pure library computation on explicit values and existing mutable hash references.
