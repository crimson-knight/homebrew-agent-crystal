# Finite native buffer ownership probe

This is an unpublished source proposal for the **memory-budget-experiment**. The implementation and guarded fixtures prepare a real native observation. Actual C compilation, Crystal compilation, native allocation/disposal, and process-memory measurements remain hosted admission gates. Local compiler/native/container/browser/SSH workload jobs are zero. The full Grant target remains 0/144.

The immediate question is whether the exact pinned `LLVM::MemoryBuffer` wrapper reaches `LLVMDisposeMemoryBuffer`, whether an idempotent guard correction changes that behavior, and whether borrowed and consuming parser inputs retain the appropriate ownership. This microprobe runs with the existing installed backend; a full compiler rebuild is a later intervention.

## Exact mechanism and source scope

`source/inputs/memory_buffer.original.cr.txt` is the exact 9c1e8ec64f6be6343e90d3979bc9536c4b050292 wrapper, SHA-256 `78205f4cb4dbbb5c3639b89903234879449b61462165165b04376a8ce7fcaabc`. The fixed copy relocates the guard transition into the operation that actually invokes the native disposer. It also adds an explicit `release_ownership` method for the consuming parser case. The restored arm copies the original bytes again.

All three arms compile the same harness and C shim. The fixed build alone receives `-Datlas_fixed_buffer`, selecting the new explicit transfer method at the consuming-IR call. The original and restored builds use the original `to_unsafe` path, exposing the old wrapper's missing transfer state. These are application-side copies of the exact wrapper under diagnostic C bindings; the installed compiler backend remains unchanged. Target-program `CRYSTAL_PATH` cannot patch that backend's internal buffer lifecycle.

The C shim resolves the exact reviewed LLVM library with `RTLD_NOW | RTLD_LOCAL`, checks LLVM 21.1.8, and checks that every selected symbol resolves to the same physical image. It calls LLVM's real create/copy, file, serialize, eager bitcode parse, consuming IR parse, verify, module/context disposal, and buffer disposal APIs. Its 256-entry registry counts entry and return around the real `LLVMDisposeMemoryBuffer` call and intercepts a second release of a retired pointer before a second native delete.

Primary LLVM sources are frozen at commit `2078da43e25a4623cab2d0d60decddf709aaea28`. [Core.cpp](https://github.com/llvm/llvm-project/blob/2078da43e25a4623cab2d0d60decddf709aaea28/llvm/lib/IR/Core.cpp) defines the caller-owned allocations and actual delete; [BitReader.cpp](https://github.com/llvm/llvm-project/blob/2078da43e25a4623cab2d0d60decddf709aaea28/llvm/lib/Bitcode/Reader/BitReader.cpp) borrows the buffer for eager parsing; [IRReader.cpp](https://github.com/llvm/llvm-project/blob/2078da43e25a4623cab2d0d60decddf709aaea28/llvm/lib/IRReader/IRReader.cpp) consumes it through a native unique pointer. Exact header declarations and license notices are included.

The shim observes real C disposer calls and consuming API calls. Caller-owned outstanding requested payload bytes are an ownership ledger. Bytes transferred to consuming IR cease to be caller-owned on either native result. The native destructor/free inside that consuming API is source-attested, with `consumed_native_destructor_observed=false`. Native heap live bytes, allocator usable sizes, mapping residency, and compiler-retained RSS remain distinct, unavailable measurements.

## Actual cases and positive controls

Each arm executes a counts run and a memory-observation run in that order, each in a fresh process. Both execute exactly the same ownership cases:

1. Allocate 64 copied 1-MiB native buffers, validate their length and first/last bytes, then call each wrapper's dispose twice and finalize once. Expected real disposal counts at that checkpoint are original/fixed/restored **0/64/0**; actual values are pending.
2. Create a known 262,144-byte file buffer and preserve the missing-file native error separately.
3. Invoke one wrapper's finalizer twice and then dispose. The original and restored source attempt a duplicate native release; the shim intercepts it. The fixed finalizer retires the guard once.
4. Serialize a valid module to bitcode, eagerly parse it through the borrowed API, dispose the caller's buffer, and verify that the independent module still contains `ret i32 42`. Invalid bitcode preserves caller ownership and its actual diagnostic text.
5. Parse valid and invalid consuming IR. The fixed wrapper transfers once before each call and retires later finalization. Original/restored stale release attempts are intercepted. Actual native error strings are retained.
6. Deliberately omit disposal of an additional held 1-MiB buffer in every arm. Its outstanding-byte increase is required before final native cleanup, including in the fixed arm.
7. Retire a separate wrapper reference and require its real GC finalizer to call the native disposer within four explicit GC rounds. This is a separately labeled sensitivity control; ordinary Grant workloads retain their normal GC policy.
8. Close every independently parsed module/context, release remaining caller-owned buffers, and require stable ownership counters across typed result serialization, zero outstanding caller-owned bytes, zero shim errors, balanced five contexts, and zero active modules. Expected totals are 73 native buffer allocations, three consuming parses, two borrowed parses, one file error, three verified useful IR observations, and 70 real disposer entries/returns. Expected intercepted nonowned attempts are 3/0/3.

The useful behavior proved here is native IR/bitcode parse/serialize/verify preservation, including use of an independent module after caller-buffer retirement. Executing a generated Grant application remains a later compiler comparison gate.
